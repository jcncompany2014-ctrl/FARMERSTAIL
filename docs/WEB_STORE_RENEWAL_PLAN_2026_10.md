# 웹 리뉴얼 기획 — "웹은 가게, 앱은 맞춤과 구독" (2026-10 초안 v0.3 — 코드 현황 반영)

> 사장님 2026-10-06: "웹이 하는 일이 결국 앱으로 가는 창구… 결제할 사람이면 더 자세한 설문을 하러 앱으로 들어올텐데
> 뭐하러 쪼개서 하나 싶다. 한국 정서랑도 안 맞는 느낌. 웹을 **제품 구매 창구(이커머스) + 앱으로 가는 중간 경로**로."
> + "단품도 점점 웹으로 옮기는 게 좋지."
>
> 이 문서는 그 방향을 **실제로 만들 수 있는 수준**까지 내린 기획이다. 화면 초안(Claude Design 4장: 홈·스토어·상세·주문완료)을
> 출발점으로, 숫자·운영·법·기존 자산까지 묶었다. 결정이 필요한 곳은 §12 에 모았다(각각 추천안 포함).

## 0. 한 장 요약

| | 지금 웹 | 바뀐 웹 |
|---|---|---|
| 첫 화면이 하는 말 | "새로 오셨어요? 1분 설문" | "이런 화식이고, **얼마**예요" |
| 파는 것 | 정기배송 하나(설문 → 결과 → 구독) | **단품**(화식 4종·체험팩·간식) — 정가, 바로 구매 |
| 설문 | 웹 라이트 설문(5문항) + 앱 정밀 설문 = 두 벌 | **앱 한 벌** — 웹은 체중 하나만 넣는 급여량 계산기 |
| 정기배송 | 웹·앱 둘 다 신청 | **앱에서만** 신청(웹은 "앱에서 15% 할인" 안내) |
| 앱으로 넘기는 순간 | 가입·결과 직전 | **박스를 받은 직후** — "얼마나 줘야 하지?"가 진짜 고민일 때 |

한 줄 원칙: **웹 = 정해진 용량을 정가에 바로 산다 / 앱 = 우리 아이 몫을 맞춰 정기적으로 받는다.**
이 선이 흐려지면(웹에서도 맞춤·구독이 다 되면) 앱에 갈 이유가 사라지고, 반대로 앱에서 단품을 팔면 웹의 존재 이유가 사라진다.

## 1. 왜 바꾸나 — 지금 구조의 문제

1. **가격이 늦게 나온다.** 홈에서 가격이 한 번도 안 보이고 모든 버튼이 설문으로 간다. 상세페이지에서 가격·구성·후기를 보고
   사는 데 익숙한 한국 소비자에게 "먼저 답해야 가격을 알려줌"은 문턱이다(미국 D2C, 특히 파머스독 모델의 관습).
2. **설문이 두 벌이다.** 웹 라이트 설문(체형 3택 등 5문항)과 앱 정밀 설문(BCS 9단계·변 상태·질환…)이 따로 있다.
   웹 설문으로 낸 결과는 어차피 앱에서 다시 정밀하게 잡아야 하고, 사장님 말대로 "결제할 사람이면 앱에 온다".
3. **"일단 한번 먹여보고 싶은" 사람이 살 게 없다.** 구독 전용이라, 체험하려면 정기결제 카드를 등록해야 한다.
   스마트스토어·쿠팡에선 단품이 팔리는데 공식몰에선 안 팔리는 역전.
4. **숫자로 보면 웹 단품의 성격이 정해져 있다(§4.2).** 5kg 강아지에게 완전 화식이면 500g 이 **이틀분**, 곁들임(30%)이면
   **약 1주분**이다. 즉 단품은 본질적으로 "체험·곁들임"이고, 제대로 먹이는 양은 정기배송 규모다 —
   그래서 "웹에서 맛보고 → 앱에서 맞춤 정기배송"이 억지가 아니라 자연스러운 흐름이 된다.

> 참고 — 지금 숫자는 판단 근거로 쓰기엔 작다(2026-10-06 기준 가입 23명, 정기배송 7건 중 서포터즈 6). 웹 설문 전환율을
> 비교할 기준값이 사실상 없으므로, 이 개편은 **원칙으로 결정하고 측정 장치를 함께 깐다**(§10).

## 2. 역할 경계 — 바꾸면 안 되는 선

| 항목 | 웹(가게) | 앱(맞춤·구독) |
|---|---|---|
| 상품 | 표준 용량 단품(500g·1kg)·체험팩·간식 | 우리 아이 맞춤 박스(그램·레시피 2종 조합) |
| 가격 | **정가** | **구독가 = 정가 −15%** (+나무 등급 10%, 서포터즈 등 기존 할인 체계 그대로) |
| 설문 | 없음(급여량 계산기: 체중 1칸) | 정밀 설문·분석·체크인·재제안 |
| 결제 | 일회 결제(카드 + 간편결제) | 정기결제(카드 빌링) |
| 배송 | 재고에서 출고(§5.4) | 주말 조리 → 화 발송(지금 그대로) |
| 계정 | 카카오 1초 가입(또는 비회원, §12-D9) | **같은 계정** — 웹 구매 이력이 앱에 그대로 |

규칙 세 줄:
- 웹에는 "맞춤"이라는 말을 쓰지 않는다. 웹의 급여량은 **"일반 기준 예상치"**, 정확한 양은 앱(같은 계산 엔진 `lib/nutrition`).
- 앱에서는 단품을 팔지 않는다(앱 = 정기배송 전용 유지). 앱 사용자가 단품을 원하면 웹 스토어 링크.
- 정가는 모든 채널 동일(자사몰·스마트스토어·쿠팡). 자사몰만의 이유는 **가격이 아니라 혜택**으로(§6.4).

## 3. 고객 여정 — 누가 어디로 들어와 어디로 가나

### 3.1 신규(검색·인스타 유입) — 가장 중요한 흐름
```
인스타/네이버 → 웹 홈(가격 보임) → 상품 상세(급여량 계산기) → 체험팩 or 500g 구매
   → 주문완료 화면 "도착하면 얼마나 줘야 할까요? 앱에서 1분" (1차 브릿지)
   → 박스 도착 · 박스 속 카드 QR (2차 브릿지, 가장 강함)
   → 앱 설치 → 같은 카카오 계정 로그인 → 구매 이력 그대로 + 정밀 설문 → 맞춤 급여량
   → 다 먹어갈 즈음(구매 후 5~7일) 앱 알림 "다음부터는 정기배송으로 15%"
```
핵심: 앱 전환을 **구매 전**이 아니라 **수령 직후**에 건다. "얼마나 줘야 하지?"가 실제 고민이 되는 순간이다.

### 3.2 재구매(이미 아는 사람)
- 웹에서 바로 재주문(주문 내역 → "같은 구성 다시 담기") 또는 앱 정기배송 전환 제안.

### 3.3 스마트스토어·쿠팡 구매자
- 마켓은 구매자 연락처를 우리가 쓸 수 없다(쿠팡 050 안심번호 — 알림톡 불가, `docs/MARKET_HUB_AND_ALIMTALK_PLAN_2026_10.md`).
- 유일한 통로 = **박스 속 카드 QR** → `farmerstail.kr/app?src=market_insert`. 마켓 고객을 자사 고객으로 데려오는 핵심 장치.

### 3.4 기존 정기배송 고객(서포터즈 포함)
- **영향 없음.** 앱 그대로. 웹으로 가입했던 고객의 관리 화면(`/account/subscriptions`)도 유지한다.

## 4. 상품·가격 설계

### 4.1 가격 (정본 `lib/pricing.ts` · DB products — 2026-07-18 확정 B세트)

| 레시피 | 100g 정가 | **500g 정가** | 1kg (안) | 앱 구독가(100g, −15%) |
|---|---|---|---|---|
| 닭고기 | 4,800 | **24,000** | 48,000 → 45,600(−5%)? | 4,080 |
| 오리고기 | 5,400 | **27,000** | 54,000 → 51,300? | 4,590 |
| 흑돼지 | 6,100 | **30,500** | 61,000 → 57,950? | 5,185 |
| 한우 | 8,300 | **41,500** | 83,000 → 78,850? | 7,055 |

> ⚠️ 화면 초안의 가격(닭 20,500·오리 24,000·흑돼지 27,000·한우 38,500)은 **7/18 이전의 옛 세트**다. 위 표가 정본.
> 1kg 할인 여부는 §12-D5. 정기배송(−15%)보다 싸지면 안 된다(앱으로 갈 이유).

### 4.2 500g 은 며칠분인가 — 상세페이지·계산기의 기준

성견·중성화·실내 기준(`lib/nutrition` BASE 1.4 × RER), 닭 130kcal/100g:

| 체중 | 하루 필요 | 완전 화식(100%) | **곁들임(30%)** | 500g 이면 |
|---|---|---|---|---|
| 3kg | 약 223kcal | 172g/일 | 52g/일 | 완전 3일 · **곁들임 약 10일** |
| 5kg | 약 328kcal | 252g/일 | 76g/일 | 완전 2일 · **곁들임 약 1주** |
| 10kg | 약 551kcal | 424g/일 | 127g/일 | 완전 1일 · **곁들임 약 4일** |

→ 상세페이지 기본 문구는 **"곁들임 기준"**으로 말한다("5kg 아이 곁들임으로 약 1주"). 완전 화식은 계산기에서 바꿔 보게.
→ 이 표가 곧 앱 정기배송의 설득 논리다: 완전 화식을 단품으로 사면 이틀마다 주문해야 한다.

### 4.3 포장 규격 — 운영상 가장 큰 변화

지금 정기배송 팩은 **강아지마다 그램이 다르다**(55g·90g·140g×14). 웹 단품은 **표준 팩**이 필요하다.
- 추천: **100g 팩** — 500g = 100g×5, 1kg = 100g×10. 해동 후 냉장 3일 안에 먹이는 규칙과 맞고(소형견 곁들임 52~76g/일),
  계산기 결과도 "하루 ○팩"으로 쉽게 말할 수 있다.
- 표준 팩은 **미리 만들어 냉동 재고**로 둘 수 있다(냉동 180일) → 주말 조리 주문 생산과 분리, 출고가 빨라진다(§5.4).
- 스마트스토어·쿠팡이 지금 쓰는 규격이 있으면 **그 규격으로 통일**(§12-D4).

### 4.3-1 상품 데이터 — 정기배송 가격과 섞지 않는다
- DB `products` 의 화식 4행은 `price`=**100g 당 정가**, `sale_price`=**100g 당 구독가**이고 정기배송 청구가 이 값을 그대로 쓴다.
  여기에 500g 단품가를 넣으면 **정기배송 금액이 깨진다.**
- → 단품은 **별도 행**으로 만든다: 예 `chicken-500g`, `chicken-1kg`, `trial-4set` — `net_weight_g`, `is_subscribable=false`,
  `sales_channel='own'`. 원재료·라벨·사진은 같은 레시피 행에서 가져오는 연결 칸 하나(예: `recipe_sku`)를 둔다.
- 정기배송 쪽 코드(`skuMap`)는 지금 4행만 보므로 영향이 없게 테스트로 잠근다.

### 4.4 체험팩
- 목적 = 4종을 다 맛보게 해서 "우리 아이 레시피"를 찾게 하는 것 → 앱 맞춤의 입구.
- 안 A: 4종 × 100g 1팩씩(400g, 정가 합 24,600원) → 체험가 [사장님 결정]
- 안 B: 4종 × 100g 2팩씩(800g, 정가 합 49,200원) → 체험가 [사장님 결정]
- DB 에 비활성 상품 `signature-4-set`(시그니처 4종 체험 세트, 19,900 → 9,950)이 남아 있다 — 이름·틀은 재사용 가능.
- 원가(포장·냉매·택배 포함)를 넣으면 손익이 바로 나오는 표를 Phase 0 에 만든다(§11).

### 4.5 간식·기타
- 활성 간식 1종: `farm-protein-mix`(팜 프로틴 믹스, 25,000원). 토퍼(헤이베일큐브·그라스큐브·가든레이어케이크)는 비활성·가격 0.
- Phase 1 은 화식 4종 + 체험팩만. 간식은 Phase 3(§11) — 상품 수가 적을 때 진열을 넓히면 오히려 비어 보인다.

## 5. 화면 기획 (모바일 우선)

### 5.1 사이트 지도

```
/                       홈 — 가격 먼저
/store                  스토어 — 탭: 화식 · 체험팩 · 간식(Phase 3)
/store/[slug]           상품 상세 — 4종 각각 + 체험팩
/store/cart             장바구니
/store/checkout         주문·결제
/store/order/[id]       주문 완료 — 앱 브릿지 #1
/p/[code]               프로모션 링크(오프라인 QR·인스타) — §9.3
/app                    앱 소개 — 지금 /why-app(AppShowcase) 재사용 + 스토어 배지·PC QR
/brand /science …       기존 브랜드·영양 근거 콘텐츠(유지, 상세에서 링크)
/faq /legal/*           유지(단품 조항 추가 §8)
/mypage/orders          주문 조회(웹·앱 공용, 지금 있음)
/recipe/[protein]       ★그대로 — 파우치 뒷면 QR 에 인쇄된 주소(바꾸면 안 됨). 상세에 "이 레시피 사기 → /store/[slug]" 한 줄만 추가
```
**왜 `/cart`·`/checkout`·`/products` 를 다시 안 쓰나**: 6월 구독 전용 전환 때 이 주소들을 **308(영구) → /start** 로 보냈다.
브라우저가 308 을 캐시하므로 같은 주소를 되살리면 예전 방문자는 계속 튕긴다 → 새 주소(`/store/*`)를 쓰고, 옛 308 의 목적지만
`/store` 로 바꾼다(색인 정리용으로 남김 — robots 로 막지 말 것, [[reference_seo_index_removal_trap]]).

옛 경로 처리: `/start` → `/app` 308(★단 `?p=코드` 는 `/p/코드` 로 — 배너에 인쇄된 QR 이 있다) · `/start/*` 설문 → `/app` ·
`/plans`(지금도 내부 링크 0 인 고아) → `/store` 308 · 웹 구독 신청(`/account/subscribe/*`) → `/app` 안내 · `/why-app` → `/app`.

헤더(모바일): 로고 · 스토어 · 앱 · 장바구니(개수). 햄버거 메뉴: 브랜드 · 영양 근거 · FAQ · 주문 조회 · 로그인.

### 5.2 홈 — 섹션 순서
1. **히어로**: 한 문장 + "닭고기 화식 500g **24,000원부터**" + [제품 보러 가기]. 사진 = 실제 그릇(생활감 톤, [[feedback_ingredient_photo_style]]).
2. **4종 가격 카드**(가로 스크롤 또는 2×2): 사진·이름·한 줄 특징·500g 가격·[담기].
3. **처음이면 체험팩**: 4종 한 번에 맛보기 — 체험가.
4. **왜 화식인가** 3줄(수비드 저온·사람 등급 원물·영양 기준) — 기존 브랜드 카피 재사용, 자세히는 /science.
5. **얼마나 먹이나** 미니 계산기(체중 → 곁들임 기준 하루 g·500g 며칠분) → 상세로.
6. **앱 띠**: "우리 아이 맞춤 정기배송은 앱에서 15% 할인" + 스토어 배지(PC면 QR).
7. **후기**(§7) · **배송 안내**(언제 오는지 한 줄) · FAQ 3개 · 법정 푸터.

### 5.3 상품 상세 — 한국 상세페이지 관습 + 우리 차별점
위에서부터:
1. 대표 사진(스와이프 3~5장: 팩·그릇·원물)
2. 이름 · 한 줄 · **가격**(500g/1kg 선택 시 바뀜) · 별점·후기 수
3. **용량 선택**(500g / 1kg) · 수량
4. **혜택 줄**: "앱 정기배송이면 15% 할인 — ○○원" / 첫 구매 혜택(있으면) / 무료배송 기준
5. **배송 안내 줄**: "오늘 주문 → ○요일 출고, 지역에 따라 하루나 이틀" (요일 약속 금지 규칙: "수요일 도착" X)
6. **급여량 계산기**(접힘 없이): 체중 입력 → [곁들임 30% | 반반 50% | 완전 100%] → 하루 ○g(○팩) · 이 용량이면 약 ○일 →
   작은 글씨 "나이·체형·활동량까지 맞춘 정확한 양은 앱에서" + [앱에서 맞춤 받기]
7. 원재료·원산지 · 보증성분(**이상·이하 표기만**, 정확한 % 금지 [[feedback_no_exact_nutrient_percent]]) · 칼로리(kcal/100g)
8. 만드는 법(수비드) · 보관·해동(냉동 −18℃ 180일, 해동 후 냉장 3일, 재냉동 금지)
9. 후기 · 상품 Q&A(테이블 `product_qna` 남아 있음)
10. 배송·교환·반품 안내(§8)
- **하단 고정 바**: [장바구니] [바로 구매] — 결제 동선은 2탭 이내.

### 5.4 배송·출고 — 화면보다 먼저 정해야 할 것
- 지금: 주말 조리 → 월 포장 → **화요일 하루 발송**(정기배송, 금요일 마감).
- 단품은 **표준 팩 냉동 재고**에서 출고하면 조리 일정과 분리된다. 추천: **화·목 주 2회 출고**(금·토 출고는 주말 택배 정체로
  냉동 품질 위험 → 하지 않음). `lib/shipping-schedule` 에 '목요일 확장' 자리가 이미 있다.
  - 예: 일~월 주문 → 화 출고 / 화~수 주문 → 목 출고 / 목 이후 주문 → 다음 화 출고
- 화면 문구는 이 규칙에서 자동 계산("지금 주문하면 10월 8일(목) 출고"). 도착 요일은 약속하지 않는다.
- 결정: §12-D8.

### 5.5 장바구니·결제

  [○○원 결제하기].
- ⚠️ **지금 토스 계약은 자동결제(빌링) 전용**이다(MID `bill_farme2odr`, 카드만, "결제위젯 키 아님" — `TOSS_GO_LIVE.md`).

## 6. 앱으로 넘기는 설계(브릿지)

### 6.1 접점 — 약한 것부터 강한 것 순
| # | 순간 | 장치 | 메시지 |
|---|---|---|---|
| 1 | 상세·장바구니 | 혜택 줄 | "정기배송이면 15% — 앱에서" |
| 2 | 주문 완료 | 큰 카드 | "도착하면 얼마나 줘야 할까요?" |
| 3 | 주문 확인 메일/알림톡 | 링크 | 같은 문장 + 앱 링크 |
| 4 | **박스 도착** | **박스 속 카드 QR** | "우리 아이 하루 양, 1분이면 알아요" — 가장 강함 |
| 5 | 배송 완료 알림 | 알림톡/메일 | 해동·급여 시작 가이드 + 앱 |
| 6 | 다 먹어갈 즈음(구매 후 ≈ 500g 소진일) | 알림톡/메일(동의 범위) | "다음엔 정기배송으로 15%" or 재구매 |

### 6.2 계정 잇기
- 웹 구매 = 카카오(또는 이메일) 계정 → 앱에서 같은 계정으로 로그인하면 주문 내역이 그대로(`/mypage/orders` 는 이미 웹·앱 공용).
- 앱 첫 진입 시 "웹에서 산 ○○ 화식이 있네요 → 강아지 등록하고 정확한 양 받기"(구매 레시피로 설문 시작점 채움).
- QR 링크는 출처를 싣는다: `/app?src=box_insert|market_insert|order_complete|mail` → 어디서 앱으로 오는지 측정(§10).
  앱 스토어를 거치면 링크 정보가 끊기므로(지금 프로모션 링크가 겪는 문제와 같다), **계정에 남기는 것**만 믿는다.

### 6.3 ⚠️ 앱이 깔린 사람이 상점 링크를 누르면 — 앱이 열린다
- 지금 iOS 유니버설 링크(`/.well-known/apple-app-site-association` — `/*` 허용)와 안드로이드 앱 링크(intent-filter 경로 제한 없음)가
  **우리 도메인 모든 주소를 앱으로 넘긴다.** 앱을 깐 사람이 인스타에서 `/store/…` 를 누르면 앱이 열리고, 앱은 같은 사이트를 띄우니
  상점 화면이 앱 안에 뜬다 — "웹 화면이 앱에 보이면 안 된다"([[feedback_web_app_never_cross]]) 위반이자, 앱은 단품을 안 판다는 원칙과도 충돌.
- → 상점 경로(`/store/*`, `/p/*`)는 **앱 링크에서 제외**한다. iOS 는 서버 파일이라 바로 반영, 안드로이드는 매니페스트라 **새 앱 빌드 필요** —
  Capacitor 보안 패치 빌드(사장님 목록 57)에 함께 싣는다. 앱 안에서 상점 링크를 만나면 외부 브라우저로 연다.
- 덤: iOS 사파리 **스마트 앱 배너**(`apple-itunes-app` 메타)가 아직 없다 — 웹 상단에 "앱에서 열기" 띠가 공짜로 생긴다(상점 페이지는 제외).

### 6.4 자사몰에서 살 이유(마켓과 겹치지 않게)
- 가격은 동일. 대신: ① 체험팩 **자사몰 단독** ② 첫 구매 혜택(기존 프로모션 엔진 확장 §9.3) ③ 앱 정기배송 연결
  ④ 후기·Q&A·영양 근거가 가장 자세한 곳. 단품을 점점 자사몰로 옮기면 마켓은 "검색 유입 + 박스 QR 로 데려오기" 역할로 남는다.

## 9. 지금 있는 것 정리 — 살리기·바꾸기·지우기

### 9.1 고객 화면
요약은 부록 A. 핵심만: **옛 상점 화면·장바구니·결제창은 6월에 코드와 테이블이 다 지워졌다 → 새로 짓는다.** 대신 결제 승인·환불·
주문 상태·재고 복원·주문 내역 화면 같은 **서버 뼈대는 살아 있다.**

### 9.2 운영(어드민) — 단품 주문이 들어오면 바뀌는 곳
- **피킹 리스트·라벨·조리 합계**는 지금 **정기배송 구독 기준**이다. 단품 주문은 별도 섹션(재고 출고)으로 — 조리 합계와 섞지 않는다.
- 송장 입력·발송 처리(오늘 고친 화면)는 주문 단위라 그대로 쓴다. 일괄 송장 입력이 필요해진다(단품 주문은 건수가 많다).
- 재고: `products.stock` 차감·복원(결제·취소), 품절 표시, 재고 부족 알림(아침 브리핑).
- 매출 보고: 정기배송/단품/서포터즈를 나눠 본다(11차 점검 D 에서 숫자가 섞이는 문제 다수 확인 — 같이 고친다).

### 9.3 프로모션 링크 — `/start?p=코드` 를 어디로
- 지금: 오프라인 QR·인스타 → 웹 설문 → 가입 시 계정에 할인이 박힘 → **첫 정기결제**에 적용.
- 바뀐 뒤 추천: `/p/코드` → 스토어(체험팩 노출) — 코드는 가입·주문 시 계정에 박히고, **웹 첫 구매**와 **앱 첫 정기배송** 중
  먼저 오는 쪽에 한 번 적용(계정당 1회 규칙 그대로). §12-D3.
- 이미 인쇄된 QR(`/start?p=코드`)은 `/p/코드` 로 넘긴다 — 배너·전단을 다시 찍지 않아도 되게.
- 주의: 지금 결제 승인 코드(`api/payments/confirm`)는 **할인액이 0 보다 크면 거부**한다(구독 전용 시절의 안전장치) → 웹 첫 구매 할인을
  하려면 이 검증을 "서버가 계산한 할인만 허용"으로 바꿔야 한다.
